# 3分钟演示脚本
0:00–0:25：定位。健康管理最难的是每天的选择；LifeOS 把记录、怎么做菜和身体趋势放在一起。先展示“规则模式”标识和隐私默认关闭。
0:25–1:05：注册并记录一餐。无密钥展示手动录入与份量修正；真实多模态演示必须预先配置并实际验证模型。展示估计而非实测的标签，保存后驾驶舱刷新。
1:05–1:35：打开「怎么做菜」，勾选手里的食材、口味和可用时间，生成菜名、分步做法与火候提示。说明无密钥时使用本地菜谱库、模型生成时会标注来源且未逐条核验；忌口仅能识别内置清单，未识别项会提示自行核实。
1:35–2:00：导入 data/health-demo.csv（明确说明是合成演示记录）；再次导入展示去重；授权健康上下文并生成规则摘要。
2:00–2:35：打开顾问，提问“下一餐蔬菜怎么选”，展示真实工作流事件和 WHO 引用。模型缺失时展示规则回答，不将其称为 LLM。
2:35–3:00：撤回授权、导出数据和删除记录。总结当前边界及下一阶段向量检索、官方移动桥接和营养数据核验。

# 答辩PPT大纲（8页）
1. 问题与用户：忙碌成年人的日常饮食选择与记录成本。
2. 核心体验：扫描/手动→修正→记录→怎么做菜→反馈。
3. 架构：Next.js、FastAPI、用户隔离数据库、服务端供应商适配器。
4. AI深度：FoodVisionAgent、NutritionPlannerAgent、HealthInsightAgent、AdvisorOrchestrator、recipes.py 本地菜谱库；区分确定性工具与模型推理。
5. 可解释与安全：估计区间、未校准置信度、知识来源、权限开关、结构校验与降级。
6. 真实测试：展示 TEST_REPORT.md，不展示未经测量的准确率。
7. 商业与社会价值：基本记录免费，后续订阅用于食谱规划与专业内容；避免出售敏感健康数据；降低健康知识使用门槛。
8. 路线图与边界：官方营养数据库、向量RAG评测、移动桥接、OAuth、安全审计。

# 创新与适用边界
已实现的价值是透明的估计与授权控制；数字孪生仅是记录摘要，不是医学预测。反事实餐食比较已实现确定性营养加法；模型Function Calling接口已实现但无真实密钥验证。长期个性化尚未交付，不作为既成功能答辩。
